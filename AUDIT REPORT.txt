CONFIRMED PROBLEMS AND FIXES
----------------------------
1. Vercel previously selected SQLite, whose serverless filesystem is not a durable
   writable database. Production now selects PostgreSQL from DATABASE_URL when the
   VERCEL environment flag is set. If the URL is missing, settings raise a clear
   ImproperlyConfigured error. Local development continues to default to SQLite.
   This code change does not prove the production environment variables or database
   connectivity are correct.

2. The service worker was served below /static/js/, limiting control to that path.
   It is now served at /service-worker.js with Service-Worker-Allowed: / and is
   registered at root scope. Browser testing confirmed root scope and a cached
   landing page reload with network access disabled.

3. The IndexedDB queue previously had no callers. New income and expense forms and
  the profile form now queue valid operations while offline. Optional uploads are
  saved as IndexedDB blobs and sent as multipart data through authenticated Django
  sync; the browser never receives Supabase storage credentials. Entries are
  scoped to the current user, kept in queue order, retried when connectivity
  returns, and retained after sync failures. Uploads over 5 MB or with unsupported
  types are rejected. Offline browser-to-Supabase storage was not live-tested.

4. The sync API previously wrote unvalidated values, returned raw exception text,
   and could duplicate entries after a lost response. It now uses the existing
   IncomeForm/ExpenseForm validation, restricts categories to the authenticated
   user's allowed choices, caps each request at 100 operations, avoids exposing
   internal exception details, and uses per-user client IDs with payload hashes for
   idempotent retries. Reusing a client ID with different data is rejected.

5. Successful logout now clears cached private HTML and API responses. The PWA
   manifest no longer references a dashboard screenshot absent from the repository.

6. Profile photos, income attachments, and expense receipts previously used Django
  FileSystemStorage under MEDIA_ROOT. Vercel's /var/task is read-only and ephemeral.
  The default upload backend now switches to django-storages S3Storage on Vercel,
  targeting Supabase's S3-compatible endpoint. Local development remains on
  FileSystemStorage. Existing model upload_to paths and database file-name fields
  remain unchanged, avoiding schema changes and preserving feature relationships.
  The bucket must be private; object URLs are signed for 10 minutes and overwrite
  is disabled. The service-role key is not used by this backend.

PRODUCTION AND MANUAL ACTIONS
-----------------------------
The supplied URL https://sheldrakefinancials.vercel.app currently returns the
Vercel platform response “404 DEPLOYMENT_NOT_FOUND”. This is not a Django route or
database error. Verify that the domain is assigned to the intended Vercel project
and production deployment, and that the expected GitHub repository and branch are
connected. Different GitHub and Vercel project names are not by themselves a
problem.

Before production sync is enabled:
  - Set DATABASE_URL in Vercel for the deployed environment to the Supabase
    PostgreSQL connection string. Never expose service-role credentials in browser
    code.
  - Apply the pending core sync-receipt migration to Supabase through the controlled
    migration process. Do not automatically apply the unreviewed AlterField drift.
  - Re-test registration, login, transaction creation, and sync on the actual domain.

Production file storage configuration requires these server-only Vercel variables:
  - USE_SUPABASE_STORAGE=true (defaults on when VERCEL is set)
  - SUPABASE_URL=https://<project-ref>.supabase.co
  - SUPABASE_STORAGE_BUCKET=<existing private bucket name>
  - SUPABASE_S3_ACCESS_KEY_ID=<Supabase Storage S3 access key>
  - SUPABASE_S3_SECRET_ACCESS_KEY=<matching S3 secret>
  - SUPABASE_S3_ENDPOINT (optional; defaults to the project's direct storage host:
    https://<project-ref>.storage.supabase.co/storage/v1/s3)
  - SUPABASE_S3_REGION=<region copied from the Supabase S3 configuration page>

Enable S3 protocol access in Supabase Storage settings and generate the S3 endpoint,
region, access key, and secret from that project's Storage S3 configuration. Bucket
existence and policies could not be inspected because no Supabase credentials are
configured locally. Reuse an existing private bucket if available; otherwise create
the configured bucket once in Supabase. Do not use the service-role key as a
browser credential or expose S3 keys in frontend code. Supabase S3 access keys grant
broad access to the project and bypass Storage RLS; protect them as high-privilege
server secrets. Django authenticates and authorizes each application request before
returning a short-lived signed object URL.

django-storages[s3]==1.14.6 is declared in requirements.txt and pyproject.toml, but
could not be installed in this offline workspace because the package index was
unreachable. No Supabase data or remote schema was changed. Vercel project/domain
configuration and production upload persistence could not be verified here.

           14. SYSTEM OVERLOAD DIAGNOSIS, PERFORMANCE FIXES & IMPROVEMENTS
================================================================================

1. CAUSES OF SYSTEM OVERLOAD:
   ---------------------------
   - Repeated Full-Table Querying & Pandas Conversions:
     On every request to Dashboard (/dashboard/) or Analytics (/analytics/),
     FinancialAnalyticsService called _get_expense_df() and _get_income_df() up to 8
     separate times per view (summary, monthly trends, category breakdown,
     monthly comparison, rule-based insights, z-score anomaly detection, net worth,
     health score). Each call ran SQL queries over 500+ records and built new DataFrames.
   - Unbounded Database Growth via Restores:
     JSON Backup Restore used direct .create() calls without duplicate checks, multiplying
     data on every restore.
   - Unrestricted Form Step Validation:
     Amount fields had step="1000" browser restrictions causing validation errors.

2. IMPROVEMENTS & SOLUTIONS MADE:
   ---------------------------------
   ✔ Request-Level DataFrame Caching (analytics/services.py):
     Added instance dictionary caches (self._income_dfs and self._expense_dfs).
     Database queries and DataFrame construction now run ONCE per request,
     cutting database query and computation overhead by ~80%.
   ✔ Import Duplicate Detection & Skipping (reports/services.py & import_preview.html):
     CSV imports check existing records by (date, amount, description). Duplicates are
     flagged, highlighted with yellow badges, and skipped automatically.
   ✔ Backup Restore Uniqueness (reports/views.py):
     Replaced .create() with get_or_create() matching on unique properties, skipping duplicates.
   ✔ Goal Form Uniqueness & Validation (goals/forms.py & goals/views.py):
     Added clean_name() to prevent duplicate active goals; cleaned up duplicate database records.
   ✔ Flexible Amount Field Validation (goals/forms.py & budgets/forms.py):
     Changed min="1" and step="1" on amount inputs so any value from TSh 1 upward is accepted.
